# TODO API

Backend-сервис для управления списком задач (to-do list), написанный на Go. Это **учебный pet-проект**: он делается не только ради самого списка задач, но и как способ последовательно пройти путь от простого HTTP-сервера до приложения, максимально приближенного по структуре и практикам к тому, что используется в реальных бэкенд-командах.

---

## Идея проекта

Правило простое: не хвататься сразу за все модные технологии, а расти по одной ступени за раз — от учебного примера с хранением данных в памяти до сервиса с базой данных, авторизацией и наблюдаемостью (логами, метриками), и на каждом шаге понимать *зачем* нужен тот или иной элемент архитектуры, а не копировать его "потому что так принято".

## Что уже реализовано

### Архитектура
Код разделён на три слоя с чёткой ответственностью:

```
HTTP-запрос → Handler → Service → Repository → База данных
```

- **Handler** — разбирает HTTP-запрос, проверяет базовую корректность данных, отдаёт HTTP-ответ.
- **Service** — бизнес-логика и правила (например, «нельзя создать две задачи с одинаковым названием»).
- **Repository** — единственное место, где происходит работа с хранилищем данных, спрятанное за интерфейсом. Благодаря этому переход с хранения «в памяти» на настоящую базу данных не потребовал переписывать ни хендлеры, ни бизнес-логику — поменялась только реализация одного интерфейса.

### Функциональность API
- Регистрация и вход пользователей (`/register`, `/login`).
- Полный набор операций над задачами: создание, получение списка, получение одной задачи, изменение, удаление.
- У каждого пользователя — собственный, изолированный список задач.
- Валидация входных данных (например, задача не может быть без названия).

### Безопасность
- Пароли никогда не хранятся в открытом виде — только хеш (bcrypt).
- Доступ к задачам защищён JWT-токеном: доступ к чужим задачам невозможен.
- Размер тела запроса ограничен (`http.MaxBytesReader`) — защита от чрезмерно больших запросов.
- Ответы на неверный логин и на технический сбой сервера разделены и не позволяют извне понять внутреннее устройство системы.

### Хранение данных
- PostgreSQL в качестве основной базы данных (драйвер `pgx`).
- Версионируемые миграции схемы базы данных (`goose`), с историей изменений.

### Надёжность сервера
- Явно настроенные тайм-ауты HTTP-сервера, чтобы «зависший» клиент не мог удерживать ресурсы бесконечно.
- Graceful shutdown — при остановке сервер сначала корректно завершает уже начатые запросы, а не обрывает их резко.
- Настройки (адрес сервера, строка подключения к базе, секретный ключ) вынесены в переменные окружения, а не «зашиты» в код.

### Логирование
- Структурные JSON-логи (`log/slog`) вместо простого текстового вывода — каждый лог можно фильтровать и анализировать по полям (метод запроса, статус ответа, длительность, ID пользователя и т.д.), как это делают реальные системы мониторинга.
- Каждый HTTP-запрос логируется на уровне middleware.
- Технические сбои (не связанные с ошибками пользователя, вроде «пароль неверный» или «задача не найдена») отдельно логируются с контекстом на уровне обработчиков — что упрощает поиск причины проблемы в проде.

### Тестирование
- Юнит-тесты для слоя хранения данных, включая проверку поведения при конкурентном доступе (`go test -race`).
- Тесты для HTTP-обработчиков через `httptest`, без поднятия настоящего сервера.
- Табличные тесты (table-driven tests) — стандартный для Go подход, когда один набор тестового кода прогоняется через таблицу разных входных сценариев.

## Технологии

| Категория | Инструмент |
|---|---|
| Язык | Go |
| HTTP-роутинг | [chi](https://github.com/go-chi/chi) |
| База данных | PostgreSQL |
| Драйвер БД | [pgx](https://github.com/jackc/pgx) |
| Миграции | [goose](https://github.com/pressly/goose) |
| Авторизация | JWT ([golang-jwt](https://github.com/golang-jwt/jwt)) |
| Хеширование паролей | bcrypt |
| Логирование | `log/slog` (стандартная библиотека) |
| Конфигурация | переменные окружения, `.env` (через [godotenv](https://github.com/joho/godotenv)) |

## Основные эндпоинты API

| Метод | Путь | Описание | Требует токен |
|---|---|---|---|
| POST | `/register` | Регистрация нового пользователя | нет |
| POST | `/login` | Вход, получение токена | нет |
| GET | `/tasks` | Список задач текущего пользователя | да |
| GET | `/tasks/{id}` | Получить одну задачу | да |
| POST | `/tasks` | Создать задачу | да |
| PUT | `/tasks/{id}` | Изменить задачу | да |
| DELETE | `/tasks/{id}` | Удалить задачу | да |

Токен передаётся в заголовке: `Authorization: Bearer <token>`.

## Что планируется дальше

Проект развивается по заранее составленному плану обучения. Дальше в очереди:

- **Docker** — упаковка приложения и базы данных в контейнеры (`Dockerfile`, `docker-compose.yml`) для одинакового запуска на любой машине.
- **Расширение API** — пагинация и фильтрация списка задач, версионирование пути (`/api/v1/...`), автоматическая документация API через Swagger/OpenAPI.
- **Наблюдаемость в проде** — метрики (Prometheus), распределённая трассировка запросов (OpenTelemetry), очереди сообщений для асинхронной обработки задач.
